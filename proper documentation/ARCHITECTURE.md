# Git In Bits: System Architecture Guide

This document provides a complete end-to-end overview of how the Git In Bits application functions, from the moment a user opens the web page to the moment the AI delivers an intelligent engineering insight.

---

## 1. The Frontend (React & Vite)
The user interface is built as a single-page application using **React**, **Vite**, and **Tailwind CSS**.
- **Role:** It acts as the visual presentation layer. It does not store sensitive data or tokens.
- **Communication:** It communicates strictly with our own backend via secure REST API calls (e.g., `/api/repos`, `/api/ai/chat`). 
- **Components:** Features like the AI Chat Widget (`AiManagerChat.tsx`) maintain their own local state (like chat history) and send messages to the backend to be processed.

---

## 2. Authentication & Login (Spring Security & OAuth2)
Git In Bits does not use traditional passwords; it relies entirely on **GitHub OAuth2**.
- **Flow:** When a user clicks "Login with GitHub", the frontend redirects them to the backend (`/oauth2/authorization/github`).
- **Backend Handling:** Spring Security intercepts this, redirects the user to GitHub to authorize the app, and then GitHub redirects them back with an authorization code.
- **Session:** The backend exchanges this code for a secure Access Token, stores the token in memory, and issues a secure HTTP-Only session cookie to the frontend. This means the frontend never actually touches the raw GitHub token, making the app highly secure.

---

## 3. Data Fetching Layer (GitHub API)
Once a user is logged in, they can request to sync a repository.
- **GitHub Client:** The backend utilizes a custom `GitHubClientImpl` to make HTTP requests to the official GitHub API on behalf of the user (using their OAuth token).
- **Pagination Engine:** Because repositories can have thousands of commits, we built a `GitHubPaginator` that automatically pages through GitHub's API limits, ensuring we download 100% of the repository's history (commits, pull requests, issues, releases).

---

## 4. The Database (MongoDB)
Raw data pulled from GitHub is transformed and stored in a NoSQL database.
- **Documents:** We map raw JSON from GitHub into Java Document objects (e.g., `CommitDoc`, `PullRequestDoc`).
- **Storage:** These documents are saved into **MongoDB** using Spring Data repositories.
- **Why MongoDB?** GitHub's data is highly unstructured and hierarchical (JSON-like). A NoSQL document database like MongoDB is perfectly suited for storing massive amounts of commits and PRs without strict relational schemas.

---

## 5. The Analysis Engine (Deterministic Metrics)
This is the core engineering intelligence of the platform.
- **The Analyzers:** When a repository is synced, the `RepositoryAnalysisService` kicks off a suite of deterministic analyzers:
  - `RepositoryStabilityAnalyzer`
  - `RepositoryRiskAnalyzer`
  - `RepositoryTrendAnalyzer`
- **How it Works:** These analyzers query the MongoDB database (e.g., "How many PRs were closed this week compared to last week?") and apply hard-coded mathematical formulas to generate a deterministic score from 0-100.
- **Result:** The system generates a factual `RepositoryAnalysisReport` containing Health Levels, Risk Scores, and concrete Concerns/Recommendations.

---

## 6. The AI Engineering Manager (Spring AI + Groq)
The final piece of the puzzle is the AI Chatbot, which acts as a Senior Engineering Manager interpreting the data.
- **The Brain:** The AI is powered by the extremely fast `llama-3.1-8b-instant` model hosted on Groq, orchestrated by **Spring AI**.
- **Agentic Workflow:** The AI is not a generic chatbot. It is configured as an autonomous agent equipped with specific "Tools" (Java functions).
- **The Tools:**
  1. `listAvailableRepositories`: Helps the AI resolve typos in repository names.
  2. `getRepositoryAnalytics`: Allows the AI to fetch the deterministic Health/Risk scores generated by the Analysis Engine.
  3. `getRepositoryEvidence`: Allows the AI to fetch the raw semantic data (recent commits, top contributors) directly from MongoDB.
  4. `getRepositoryTimeline`: Allows the AI to query the very first commit and total lifetime metrics.
- **The Magic:** When you ask the AI a question (e.g., *"Why is this repo risky?"*), it first calls the tools to read the actual database. It then synthesizes the mathematical scores with the raw commit evidence to give you a highly accurate, non-hallucinated answer!
